Here is the finalized GOC Royale — Game Design Document v1.0, structured as a build-ready specification for ChatGPT Work or a development team.

It locks in exactly two pilot modes, seven playable fighters, and the multiplayer requirements. It also separates launch requirements from future additions to prevent the project from expanding before the core game is playable.

# 1. Product Overview

## 1.1 Game Concept

**GOC Royale** is a fast-paced, multiplayer arena combat game featuring exaggerated cartoon representations of Grace on Campus ministry leaders.

Each playable fighter has unique attacks, movement characteristics, statistics, and a powerful Super ability inspired by their ministry team's responsibilities.

Players join private rooms through a room code or invitation link, select their favorite leader, and compete against their friends.

The game is inspired by the accessible, competitive gameplay of top-down hero brawlers such as Brawl Stars, but must have its own original characters, visual identity, interface, maps, and gameplay presentation.

The pilot features two game modes:

**Showdown FFA:** A battle-royale-inspired free-for-all in which players fight to become the last survivor as the arena gradually shrinks.

**Broomball:** A 3v3 hockey-inspired game based on GOC's broomball tradition. Players battle for possession of a ball and score goals using directional passing, shooting, positioning, and their fighters' unique abilities.

The goal is to make a genuinely entertaining multiplayer game that happens to feature recognizable GOC personalities.

It should not feel like a ministry administration simulator or educational application.

## 1.2 Design Philosophy

The game must prioritize five principles.

### 1. Fun Before Complexity

Moving, aiming, attacking, dodging, scoring, and eliminating opponents must feel satisfying before additional systems are introduced.

A simple, polished game is preferable to a feature-rich but unreliable game.

### 2. Mobile-First Interaction

The game must be fully playable on a mobile browser.

The interface should feel like a native mobile action game, with comfortable dual-thumb controls and clear visual feedback.

### 3. Meaningfully Different Fighters

Every leader must have a distinct gameplay identity.

Changing characters should meaningfully alter the player's combat strategy rather than simply changing the sprite and attack color.

### 4. Short, Repeatable Matches

Players should be able to finish a match within approximately three minutes and immediately start another.

The experience should work for casual friend-group game nights.

### 5. Low Friction

Players should not need to install an application, create an account, or configure complicated settings.

Joining through a room code or link should be enough.

# 2. Pilot Scope

## 2.1 Required Launch Features

The initial release must include:

1. Seven unique playable fighters: Brandon Kam, Daniel, Rich, Samuel, Josh, Elijah, and Ethan Ha.
2. Character-specific basic attacks.
3. Character-specific Super abilities.
4. Health, damage, ammunition, reloading, cooldowns, healing, and eliminations.
5. Smooth multidirectional movement.
6. Directional aiming and attacking.
7. **Showdown FFA** with permanent round eliminations, a shrinking arena, and survival rankings.
8. **3v3 Broomball** with ball possession, directional passing, shooting, goals, scoring, and respawning.
9. One complete arena for each game mode.
10. Landscape mobile controls and desktop keyboard/mouse controls.
11. Private multiplayer rooms with codes and invitation links.
12. Character selection and ready-up lobby.
13. Real-time synchronized multiplayer gameplay.
14. Host-authoritative combat, collisions, cooldowns, and scoring.
15. Results screens showing relevant player statistics.
16. Rematch functionality.
17. Original cartoon character artwork or original illustrated placeholders.
18. Basic animations, attack effects, Super effects, and sound.

## 2.2 Explicitly Out of Scope

Do not implement the following as part of the pilot:

- Additional playable fighters.
- Additional game modes.
- Character leveling or upgrades.
- Equipment and item inventories.
- Monetization.
- Purchasable skins.
- Global leaderboards.
- Ranked matchmaking.
- Public matchmaking.
- Persistent accounts.
- Achievements and progression systems.
- In-game voice chat.
- Full replay recording.
- Character gadgets.
- Character passive abilities.
- Combination Supers.
- Power-up crates or loot systems.
- Spectator slots for people who were not participating in the match.
- Multiple maps per game mode.

These features may be considered after successful testing of the pilot.

**Development rule:** Do not implement future features at the expense of completing or polishing the required gameplay.

# 3. Core Combat System

## 3.1 World Coordinates

Use a consistent 2D world-coordinate system.

Recommended values:

| Property                 | Initial Value                 |
| ------------------------ | ----------------------------- |
| Player collision radius  | 0.42 world units              |
| Normal movement speed    | 5.2 units/second              |
| Fast movement speed      | 5.8 units/second              |
| Slow movement speed      | 4.6 units/second              |
| Basic attack ammo        | Character-specific            |
| Basic attack reload      | Character-specific            |
| Super charge requirement | 5,000 effective charge points |
| Passive heal delay       | 4 seconds                     |
| Passive healing          | 12% max HP per second         |
| Client rendering target  | 60 FPS                        |
| Host simulation rate   | 30 ticks/second               |

These values are initial balancing targets, not immutable requirements.

Use frame-rate-independent movement and physics.

## 3.2 Movement

Characters move freely in two dimensions.

Movement must include:

- Analog directional movement.
- Normalized diagonal movement.
- Smooth starting and stopping.
- Collision with solid terrain.
- Movement speed modifiers.
- Knockback.
- Temporary stun and slow effects.
- Movement while aiming.

Characters cannot move through walls or outside arena boundaries.

Teammates should not physically block one another.

Movement should feel responsive rather than floaty.

Broomball may use subtly different acceleration and friction to convey movement on ice, provided controls remain precise.

## 3.3 Health and Damage

Each character has a maximum HP value.

Successful damaging attacks subtract HP.

When HP reaches zero, the character is eliminated.

Implement:

- Direct projectile damage.
- Area-of-effect damage.
- Multi-hit attacks.
- Healing.
- Damage-over-time from arena hazards.
- Temporary protective status effects where specified.
- Invulnerability during designated respawn protection windows.

Health cannot exceed maximum HP.

Damage cannot reduce health below zero.

The browser host is authoritative over health values.

## 3.4 Basic Attacks and Ammunition

Each fighter has character-specific attack statistics.

All fighters begin with full ammunition.

Each attack consumes one ammo charge.

Spent ammo reloads sequentially according to the fighter's reload time.

A player cannot attack without available ammunition.

Attack direction is determined by the player's aim input.

Basic attacks must display:

- Attack animation.
- Projectile or area effect.
- Hit feedback.
- Damage indicators.
- Appropriate sound feedback.

No attack may be fired more frequently than its defined rate.

## 3.5 Super Charge System

Players charge their Super through successful combat actions.

Suggested charge formula:

- 1 damage dealt to enemies = 1 charge point.
- 1 effective HP healed on allies = 0.6 charge points.
- Self-healing does not generate charge.
- Damage from Super abilities does not generate charge.

A Super becomes available at 5,000 charge points.

The meter resets to zero when a valid Super activation succeeds.

A Super activation that fails host validation should not consume the meter.

Supers must have:

- Character-specific effects.
- Clear visual indicators.
- Host-validated activation.
- Correct targeting.
- Appropriate collision checks.
- Distinctive animations and sound.

Super charge persists through normal Broomball respawning.

## 3.6 Passive Healing

Players begin regenerating health after four continuous seconds without receiving damage or using a basic attack.

Healing rate: 12% of maximum HP per second.

Receiving damage or using a basic attack restarts the healing delay.

Passive healing stops at maximum HP.

In Showdown, passive healing is important to make multiple encounters survivable.

## 3.7 Status Effects

The combat engine must support at least:

- **Slow:** Reduces movement speed by a percentage.
- **Stun:** Temporarily prevents movement and attacking.
- **Knockback:** Pushes a character in a direction.
- **Reveal:** Makes a hidden target visible to opponents.
- **Healing:** Restores HP over time or instantly.
- **Invulnerability:** Prevents damage for a defined duration.

Effects should use standardized definitions so that abilities are consistent and maintainable.

Status-effect durations must be tracked by the browser host.

Multiple slowing effects should not stack additively without a defined cap. For the pilot, use the strongest active slow.

## 3.8 Collision Model

The browser host validates collisions involving:

- Players and solid walls.
- Projectiles and walls.
- Projectiles and players.
- Explosions and players.
- Characters and arena boundaries.
- Broomball and terrain.
- Broomball and players.
- Broomball and goal areas.

Fast-moving projectiles should use swept collision detection or equivalent methods to prevent tunneling through targets.

All collision dimensions should be defined in shared gameplay data.

# 5. Game Mode One: Showdown FFA

## 5.1 Overview

Showdown is a free-for-all survival game.

Every player fights independently.

The objective is to become the last player standing.

Players are eliminated permanently for the current match.

There are no teams and no respawning.

## 5.2 Player Count

- Minimum: 2 players.
- Recommended: 4–8 players.
- Maximum: 8 players.

A lobby can launch Showdown with any valid player count.

The mode should support different player counts without requiring bots.

## 5.3 Match Flow

1. Players select fighters and ready up.
2. The browser host assigns distinct spawn positions.
3. A three-second countdown begins.
4. All players spawn at full HP and ammunition.
5. Players fight and reposition.
6. The arena's safe zone begins shrinking.
7. Players outside the safe zone receive increasing damage.
8. Eliminated players enter spectator mode.
9. The match ends when one player remains alive.
10. Final placement and combat statistics appear.

## 5.4 Arena: Central Lawn

**Theme:** Stylized campus lawn with bushes, paths, benches, and colorful obstacles.

Recommended logical dimensions: 36 × 24 world units.

Map elements:

- Central open combat area.
- Decorative campus-themed terrain.
- Bushes for concealment.
- Solid stone obstacles.
- Destructible crates used as cover, without loot drops.
- Side passages.
- Several balanced starting locations.

The map should be symmetrical enough to avoid obvious spawn advantages while still feeling visually varied.

## 5.5 Spawn Rules

Players spawn at predetermined valid points distributed around the arena.

The spawn system must:

- Maintain a reasonable minimum separation between players.
- Avoid spawning anyone inside obstacles.
- Avoid selecting neighboring spawn locations when distant locations are available.
- Avoid placing players within immediate unavoidable attack range of another player.

Use the browser host to select spawn positions.

## 5.6 Shrinking Arena

A visible circular safe zone gradually shrinks over the course of the match.

Proposed progression:

| Elapsed Time    | Safe Zone                         |
| --------------- | --------------------------------- |
| 0–20 seconds    | Full starting area                |
| 20–70 seconds   | Gradually shrinks to 75%          |
| 70–120 seconds  | Gradually shrinks to 45%          |
| 120–150 seconds | Gradually shrinks to 20%          |
| 150–180 seconds | Shrinks toward a small final area |

Percentages refer to the original safe-zone radius.

The circle's center may move toward a predetermined final destination, but the complete sequence must be chosen by the browser host.

The final destination should be a reachable location with reasonable cover and no inaccessible areas.

### Danger Zone Damage

Players outside the safe zone take damage every second.

Initial values:

- Early phase: 350 HP/second.
- Middle phase: 650 HP/second.
- Late phase: 1,100 HP/second.
- Final phase: 1,800 HP/second.

Damage should be applied continuously or in small host-authoritative intervals.

Damage indicators must make it obvious when a player is outside the safe zone.

A warning animation should appear shortly before each major shrink phase.

## 5.7 Elimination and Placement

When a player reaches zero HP, they are eliminated.

Placement depends on elimination order.

Example:

- First player eliminated in an eight-player match: 8th.
- Second player eliminated: 7th.
- Final surviving player: 1st.

For simultaneous eliminations, use deterministic host event ordering, with ties allowed if events are truly simultaneous.

The browser host should end the round when one survivor remains.

If an unusual stalemate prevents completion after the final danger phase, use a hard match limit of 210 seconds and resolve remaining placements deterministically by remaining health percentage, then damage dealt.

## 5.8 Spectator Mode

Eliminated players automatically enter spectator mode.

They can:

- Observe surviving characters.
- Switch between surviving players.
- View remaining player count.
- View match progression.

They cannot attack, move a fighter, or influence gameplay.

Spectators remain connected to the room and receive match results.

## 5.9 Showdown Results

Display:

- Final placement.
- Winner.
- Eliminations.
- Damage dealt.
- Damage received.
- Healing performed.
- Survival time.

The winner receives a distinctive victory presentation.

Offer Rematch and Return to Lobby actions.

# 6. Game Mode Two: Broomball

## 6.1 Overview

Broomball is the pilot's signature team-based mode.

It combines top-down arena combat with hockey-inspired scoring and movement.

Two teams of three attempt to score goals using a shared ball.

The game is inspired by GOC's broomball tradition and should have a distinct icy rink aesthetic.

**Blue Team:** 3 fighters.\
**Red Team:** 3 fighters.

## 6.2 Victory Conditions

Match duration: 150 seconds.

A team wins when:

- It scores two goals, or
- It has more goals when the timer expires.

If the match ends tied, begin 30 seconds of golden-goal overtime.

The first team to score in overtime wins.

If overtime expires without a goal, the match ends in a draw.

The match timer and score are controlled by the browser host.

## 6.3 Arena: Broomball Night

**Theme:** A stylized ice rink inspired by GOC's traditional broomball outings.

Recommended logical dimensions: 34 × 20 world units.

Visual elements:

- Light-blue ice surface.
- Hockey-style markings.
- Blue and red goal areas.
- Rink boards.
- Decorative bleachers.
- Colorful lights.
- Optional GOC-inspired banners.
- Minimal environmental obstacles.

The center should be open enough to support passing and coordinated offensive movement.

### Goal Locations

Blue goal: left side.

Red goal: right side.

Goals should have a clearly defined opening, scoring plane, and collision geometry.

Suggested goal opening: 4 world units wide.

Goal detection occurs only when the free ball crosses the goal plane in the valid scoring region.

Carrying the ball directly into the goal should not automatically score; the player must release it.

Own goals count for the opposing team.

## 6.4 Ball Possession

A free ball can be acquired by touching it.

Ball states:

1. **Free:** Moving or stationary on the rink.
2. **Carried:** Attached to a player.
3. **In Flight:** Traveling after being shot or passed.
4. **Resetting:** Temporarily inactive after a goal or kickoff.

A free or in-flight ball becomes carried when it collides with a valid player who is eligible to receive possession.

An in-flight ball may be intercepted.

To avoid immediate accidental reacquisition, the player who released or lost the ball cannot reacquire that same ball for approximately 0.4 seconds.

The browser host is authoritative over possession.

Only one player may possess the ball at a time.

## 6.5 Controls While Carrying the Ball

When a player gains possession:

- The normal attack joystick changes into a pass/shoot joystick.
- The attack icon changes to a ball or broom icon.
- Basic attacks become unavailable.
- The Super button becomes unavailable.
- The player's ammunition is preserved.
- Movement remains available.

This introduces an important tactical choice:

**Players can carry and shoot the ball, or use their combat abilities, but not both simultaneously.**

The UI should make the change immediately obvious.

## 6.6 Passing and Shooting

Both passing and shooting use the same directional control.

The player drags the right-side control toward an intended direction.

Releasing launches the ball.

Initial power model:

- Short drag: low-power pass.
- Medium drag: medium-power pass or shot.
- Long drag: high-power shot.

Map normalized drag distance to a launch power between 0.35 and 1.0.

Suggested ball launch speed:

- Minimum: 8 units/second.
- Maximum: 16 units/second.

The player can aim in any direction.

Do not automatically redirect shots toward a goal or teammate.

Ball direction and power must be validated by the browser host.

The control should display an aiming line and approximate shot direction.

## 6.7 Ball Physics

The ball should:

- Travel smoothly.
- Decelerate gradually from ice friction.
- Bounce off rink boards.
- Interact with player collision circles.
- Enter either goal through its valid opening.
- Remain synchronized across clients.

Suggested physics:

- Ball radius: 0.32 world units.
- Board collision restitution: approximately 0.8.
- Friction: tuned so an unimpeded high-power shot can travel most of the rink.

Use continuous or swept collision detection to avoid high-speed ball tunneling.

Ball movement and scoring must be simulated on the browser host.

For the pilot, prioritize consistent physics over advanced realism.

## 6.8 Defending and Interceptions

Defenders can stop scoring opportunities by:

- Moving into the ball's trajectory.
- Intercepting passes.
- Attacking the carrier.
- Using knockback abilities.
- Using stuns.
- Positioning near the goal.
- Blocking shooting lanes.

A player who touches the ball while it is free or moving can gain possession, provided pickup eligibility rules are satisfied.

The ball should remain a physics object, not a projectile that automatically passes through players.

## 6.9 Dropping the Ball

The ball carrier loses possession when:

- The carrier is eliminated.
- A qualifying knockback effect strikes the carrier.
- A stun successfully affects the carrier.
- The carrier voluntarily passes or shoots.

Ordinary damage alone does not automatically cause a drop.

When forcibly dropped:

- The ball appears at the player's current location.
- It receives a small separation impulse.
- The former carrier receives the standard reacquisition lockout.
- The ball becomes available to other players.

The ball must never remain attached to an eliminated or disconnected character indefinitely.

## 6.10 Fighter Abilities in Broomball

Characters retain their standard attacks and Supers while not carrying the ball.

Examples:

- Brandon creates a slowing zone near the goal.
- Daniel charges through opposing defenders.
- Rich stuns players preparing to intercept.
- Samuel protects teammates during an attack.
- Josh pushes opponents away from scoring lanes.
- Elijah repositions using his rollback ability.

Supers cannot be activated while holding the ball.

Existing active effects can continue after a player picks up the ball.

Avoid introducing separate Broomball-exclusive versions of every fighter's Super.

## 6.11 Respawning

When eliminated in Broomball:

1. The player drops the ball if carrying it.
2. The opposing team receives no elimination score toward victory.
3. The character enters a three-second respawn timer.
4. The character respawns near their team's side.
5. HP and basic ammunition return to full.
6. The player gains 1.5 seconds of spawn protection.
7. Protection ends immediately if they attack.

Super charge remains unchanged after respawning.

Spawning should occur behind the team's defensive zone, away from immediate enemy pressure.

## 6.12 Goal Scoring

A goal occurs when the ball crosses a valid goal plane.

Upon scoring:

1. The browser host confirms the goal.
2. The scoreboard updates.
3. The ball becomes inactive.
4. A goal animation and sound play.
5. The scoring team receives credit.
6. Player possession is cleared.
7. After a short celebration, both teams reset to kickoff positions.
8. The ball returns to center.
9. Players resume after a brief countdown.

Reset player health and ammunition to full on kickoff.

Preserve Super charge so that Supers remain meaningful during short matches.

## 6.13 Broomball Statistics

Track:

- Goals scored.
- Assists.
- Eliminations.
- Deaths.
- Damage dealt.
- Healing performed.

An assist is credited to the most recent teammate who passed the ball to the goal scorer within the previous eight seconds, provided the opposing team did not gain possession afterward.

Advanced statistics such as saves and shot accuracy can be added later.

## 6.14 Broomball Results Screen

Display:

- Winning team.
- Final score.
- Player goals.
- Player assists.
- Eliminations and deaths.
- Damage dealt.
- Healing performed.
- Match MVP.

The MVP calculation should reward scoring and assists alongside combat contributions.

- Active match: 20 seconds.

- In Showdown, eliminate the fighter without granting another player a kill.
- In Broomball, remove the inactive fighter from play and clear their ball possession, if applicable.

Do not invent a replacement bot unless bot support is explicitly added later.

Matches should remain playable if a participant disconnects, though the user interface should indicate the missing player.

# 10. Visual Art Direction

## 10.1 Overall Aesthetic

All seven fighters use painterly, anime-inspired chibi 3D: coherent sculpted forms, expressive faces, articulated hands, believable stylized clothing and dynamic motion. Begin around 2.8–3.2 heads tall, then review each silhouette at the overhead game camera. Low polygon count is an optimization technique, not a blocky or toy-like visual treatment.

Follow [ART-AND-AUDIO-DIRECTION.md](ART-AND-AUDIO-DIRECTION.md) for palette, shading, environments, UI and sound; [CHARACTER_3D_PIPELINE.md](CHARACTER_3D_PIPELINE.md) governs the common eight-pass modeling workflow. Runtime constraints and acceptance remain governed by [PERFORMANCE-AND-GAMEPLAY-STANDARDS.md](PERFORMANCE-AND-GAMEPLAY-STANDARDS.md). The art update does not change gameplay, collision, timing or network authority.

## 10.2 Character Visual Concepts

- **Brandon:** Beige jacket, fitted glasses, clipboard and nametags; retain readable welcome effects.
- **Daniel:** Broad silhouette, keys and blue utility-vehicle motifs.
- **Rich:** Camera, flashes and lavender/cream lens motifs.
- **Samuel:** Snack bag, warm mustard clothing and mint healing effects.
- **Josh:** Speaker/mixer equipment and orange soundwaves.
- **Elijah:** Laptop, teal/ink clothing and green/cyan digital effects.
- **Ethan Ha:** Dark tee, gray joggers, plum/gold music accents, Rizz notes and Aura Pulse; guitar remains a proposed visual prop.

These are fictionalized visual briefs. Record reference provenance and unresolved likeness decisions; the other five fighters currently lack supplied likeness references. Every fighter needs an individual asset specification before production modeling. Brandon's specification is the first example, not permission to copy his face, jacket or choreography onto everyone.

## 10.3 Modeling and Animation Requirements

Every fighter follows eight passes: references/proportions, primary sculpt, garments/secondary forms, deforming mesh/rig, textures/browser look, face/grip/garment proof, first gameplay clips, and optimization/integration.

Require a shaped expression-ready face, both hands with four articulated fingers and an opposable thumb, garment construction and major folds, tested skin weights and authored garment follow-through. Bake fine creases into portable maps where appropriate. Runtime cloth simulation is not required. Validate actual prop grips and release poses for each character; a reused rig is not a passed deformation test.

The first animation proof is a close-up face/grip/garment performance, followed by idle, run and basic attack. Live integration requires the full animation set from performance standard section 7: directional locomotion, basic attack, Super, hit, disabled, elimination, respawn, victory, and Broomball carry/release, with tested transitions and event markers. Feet and held objects must remain stable. Motion stays in-place and gameplay truth remains authoritative; no added cast delay, collision reach or damage radius.

Sprite transformations and old mitten/static-face studies are prototype history, not acceptance substitutes for the new 3D assets. Confirm portable shading and animation in the browser and test eight fighters plus effects on physical target phones before declaring production readiness.

# 12. Technical Architecture

## 12.1 Recommended Stack

**Current client implementation**

- TypeScript
- Phaser 3 for the current 2D presentation; shared TypeScript owns authoritative simulation and collision
- React for menus, lobby, character selection, and results
- Vite for development and builds

**3D presentation target:** the new asset pipeline describes planned production art. Separate 3D studies are not a completed multiplayer renderer migration. Use one live arena renderer when integrating 3D, preserve the existing simulation coordinate system, and meet the performance standard before rollout.

**Browser Host**

- The room creator’s browser runs the authoritative TypeScript fixed-timestep simulation.
- PeerJS / WebRTC data channels carry inputs and snapshots between the host and guests.
- Public PeerJS signaling and STUN discovery support connection setup.
- No Node.js application server, Socket.IO, database, or persistent paid backend is deployed.
- TURN may be configured for networks that cannot connect directly; relay availability and cost are external constraints.
- The host must keep the room tab open and active. Host migration is outside this pilot implementation.

**Shared**

- TypeScript gameplay definitions, character statistics, message schemas, maps, and collision constants.
- Rendering, simulation, and transport remain separate modules.

**Infrastructure**

- Static HTTPS hosting, compatible with a free static hosting tier.
- WebRTC encrypted data channels for live gameplay.
- Temporary rooms and results live in the host tab’s memory.
- Host authority trusts the room creator; it cannot prevent a modified host from cheating.

This architecture supersedes the original Node/Socket.IO recommendation by user decision on October 23, 2026.

## 12.2 Suggested Repository Layout

- `client/` — Web game, Phaser scenes, React UI, touch controls.
- `shared/room.ts` and `client/src/network.ts` — Rooms, host simulation lifecycle, and WebRTC transport.
- `shared/` — Shared types, fighter data, gameplay constants, protocol schemas.
- `client/public/art/` — Original sprites, sounds, map art, fonts, and effects.
- `tests/` — Gameplay tests, room tests, and browser-based end-to-end tests.
- `docs/` — Game design documentation, networking protocol, testing checklist.

The project should separate game rendering from authoritative game logic.

## 12.3 Host-Authoritative Model

The browser host must own:

- Player positions.
- Player HP.
- Ammunition.
- Reload state.
- Super charge.
- Status effects.
- Projectiles.
- Collision results.
- Elimination state.
- Respawn timers.
- Showdown safe zone.
- Broomball position and velocity.
- Broomball possession.
- Scoring.
- Match timer.
- Win conditions.

Clients should send player intentions, not final outcomes.

For example, clients send:

- Movement direction.
- Aim direction.
- Attack input.
- Super input.
- Ball shot direction and requested power.

Clients must not be allowed to submit arbitrary damage, positions, health changes, goals, or eliminations.

## 12.4 Simulation Timing

Recommended initial configuration:

- Host simulation: 30 Hz.
- Client input transmission: up to 30 Hz.
- Host snapshots: approximately 30 Hz.
- Client rendering: target 60 FPS.
- Remote player interpolation buffer: approximately 100 milliseconds, tunable.

Use sequence-numbered inputs and host timestamps.

The host simulation should use a fixed timestep independent of rendering performance.

## 12.5 Client-Side Prediction

Implement local prediction for player movement.

The client should:

1. Read local movement input.
2. Predict the local character's movement.
3. Send sequenced inputs to the browser host.
4. Receive authoritative snapshots.
5. Reconcile local prediction with authoritative state.
6. Replay unacknowledged inputs when necessary.

Apply interpolation to remote players and appropriate visual smoothing.

This is essential for responsive mobile gameplay.

## 12.6 Projectile and Combat Synchronization

Projectiles should have unique host-generated identifiers.

The browser host validates:

- Attack availability.
- Ammo.
- Fire rate.
- Aim vectors.
- Spawn position.
- Projectile travel.
- Collision.
- Damage.
- Elimination.

Clients may immediately display cosmetic attack feedback, but authoritative hits and damage must be confirmed by the browser host.

## 12.7 Broomball Synchronization

Ball state is especially important because possession and goals are contested.

Represent ball state explicitly:

- Ball ID.
- Position.
- Velocity.
- State.
- Carrier ID, if any.
- Last releasing player.
- Pickup eligibility or cooldown.
- Last relevant teammate pass.
- Host timestamp.

The browser host alone determines:

- Ball acquisition.
- Ball release.
- Ball collision.
- Possession transfer.
- Goal detection.
- Goal reset.

Clients should interpolate ball movement and smoothly transition between free and carried states.

## 12.8 Room Lifecycle

Use an explicit room-state machine:

**Waiting → Character Selection / Ready → Countdown → In Match → Results → Waiting**

Support disconnect/reconnect transitions without allowing contradictory room states.

Room codes must be unique among active rooms.

Expired rooms should be cleaned up automatically.

Recommended cleanup:

- Abandoned empty room: 30 minutes maximum idle lifetime.
- Completed room with no connected players: delete after a short grace period.

Use temporary, expiring session data.

## 12.9 Network Safety and Validation

Validate all incoming messages.

Enforce:

- Movement vector limits.
- Attack rate limits.
- Super activation requirements.
- Ball shot power bounds.
- Valid room membership.
- Allowed actions for the player's current game state.
- Legal character selections.
- Legal team assignments.
- Maximum message size and input frequency.

Reconnect tokens should be unpredictable and kept separate from public room codes.

Rate-limit room creation and code guessing.

Do not trust client timers or client-generated gameplay outcomes.

## 12.10 Deployment

Build static assets with `npm run build` and deploy `dist/` to an HTTPS static host.

No long-lived Node process, Socket.IO endpoint, database, or serverless gameplay function is required. Signaling is provided by PeerJS Cloud by default. The creator’s tab performs live simulation. If the host closes or reloads, the room ends; create a fresh room to continue.

Do not promise universal zero-cost connectivity: restrictive networks can require TURN relay access, and third-party free service terms or availability may change. Direct WebRTC is the default first-use implementation.

## Camera and responsiveness

A 1.65x arena-fit camera follows the local fighter or selected spectator target, clamped to map edges. Host simulation and snapshots run at 30 Hz.
